# Changelog

All notable changes to this project.

## [Unreleased]

- [FEATURE] The target OpenAPI version is a build option on every public Core surface: `OpenApiDocumentOptions.OpenApiVersion` and `SchemaOptions.OpenApiVersion` (`Microsoft.OpenApi.OpenApiSpecVersion`, default `OpenApi3_0`). A document is built for that version and is supported only when serialized into the same version. The CLI parses `--openapi-version` once and uses the value for the build, the validation and the serialization. Output does not change yet: the option is the carrier for version-dependent forms.
- [BEHAVIOR] A version other than 3.0, 3.1 or 3.2 (`OpenApi2_0`, or a value outside the enum) makes `OpenApiDocumentBuilder.Build`, `OpenApiDocumentBuilder.BuildWithValidation` and `new SchemaGenerator(...)` throw the new public `OpenApiConfigurationException` (derived from `InvalidOperationException`) before the assembly is loaded. `BuildWithValidation` takes the validation version from the build options when `ValidationContext.OpenApiSpecVersion` is `null`; an explicit value that differs from `OpenApiDocumentOptions.OpenApiVersion` now throws `OpenApiConfigurationException`. Library callers that set `ValidationContext.OpenApiSpecVersion` to 3.1 or 3.2 must set the same `OpenApiVersion` in the build options. The CLI exit code for an unknown `--openapi-version` stays 2.

- [FEATURE] Public diagnostics channel. Warnings produced while extracting are now `ExtractionDiagnostic` records (`Code` from `ExtractionDiagnosticCodes`, `Message`, `Location`, `Subjects` and, for version-related warnings, `TargetVersion`, `Feature`, `Action`, `ExtensionName`, `RequiredVersion`), delivered to `OpenApiDocumentOptions.OnDiagnostic` or `SchemaOptions.OnDiagnostic`. Library callers no longer need to capture `Console.Error`. Without a subscriber every warning is printed to stderr with its previous text, so CLI output is unchanged. The public extractors (`SecuritySchemeExtractor`, `JsonOptionsExtractor`, `PathBaseExtractor`, `ResponseHeaderExtractor`, `GlobalMediaTypesExtractor`) get overloads taking an `Action<ExtractionDiagnostic>?`; the existing signatures still print to stderr.
- [BEHAVIOR] Within one build, a warning repeated with the same code, place and text is reported once (for direct schema generation: once per `SchemaGenerator` instance). Previously, for example, a security scheme registered three times printed the duplicate warning twice.
- [FEATURE] New public `OpenApiExtractionException` (derived from `InvalidOperationException`, with `TypeName` and `MemberName`) for annotations that are provably wrong; it is not raised yet.

- [BUGFIX] Two different closed generic types whose component id came out the same — for example `A.Page<Item>` and `B.Page<Item>`, both `ItemPage` — silently shared one component, so the second response was described by the first type's schema. Every component id is now reserved per CLR type: the second type gets the fallback id (`Item` + the full name of its generic definition with `.`/`+` → `_`, e.g. `ItemB_Page`), and a numeric suffix if that is taken too. Ids that did not collide are unchanged, including the existing full-name fallback for two non-generic types with one short name. OpenAPI 3.0 output changes only for documents that had such a collision.

- [FEATURE] With the OpenAPI 3.0 target, a GET, HEAD or DELETE operation that has a request body now gets one warning naming the method and path: OpenAPI 3.0 supports `requestBody` only on methods whose HTTP semantics define a body, so 3.0 consumers must ignore it. The output is unchanged; 3.1 and 3.2 targets, where such a body is allowed, get no warning. Warnings of this kind are delivered after the document is final, so operations on excluded paths are never reported, and their order is deterministic.

- [BUGFIX] Actions declared with `[AcceptVerbs]` are no longer lost. Each method of `[AcceptVerbs("GET", "POST")]` or `[AcceptVerbs("PUT")]` becomes an operation on the attribute's `Route`, and methods from `[AcceptVerbs]` and `[Http*]` on one action are united without duplicates. An empty `[AcceptVerbs()]`, or a custom attribute derived from `HttpMethodAttribute` whose methods are not visible in metadata, skips the action with a warning instead of guessing a method from the attribute's name; a subclass of a built-in `[Http*]` attribute keeps that attribute's method. `ActionDiscovery.DiscoverActions` gets overloads with an `onDiagnostic` callback, and `ActionInfo` gets `OperationName` (the attribute's `Name`) and `AttributeOrder`. OpenAPI 3.0 output changes only for projects that use `[AcceptVerbs]` or such subclasses: the operations appear.

- [BUGFIX] When several actions declare the same path and HTTP method, the document keeps one chosen by an ordinal key — controller type full name, action method name, parameter type full names (overloads), attribute order in metadata — instead of the last one discovered, and a warning names every action involved. `--validate` locations point at the same winning action (previously at the first one discovered, while the document showed the last). Operations on excluded paths are not reported. OpenAPI 3.0 output changes only where such a conflict exists.
- [BEHAVIOR] An operation's `operationId` falls back to the `Name` of the attribute that produced that operation (`[HttpGet(Name = …)]`, `[AcceptVerbs(…, Name = …)]`). Previously the first `Name` found on any `[Http*]` attribute of the method was used for every operation of the method. When one action declares the same method and route twice (`[HttpGet(Name = …)]` and `[AcceptVerbs]`), the first given `Name` is kept; two different names keep the first with a warning. No id is ever synthesized; an explicit `[SwaggerOperation(OperationId)]` is shared by all operations of a multi-method action and left for `operation.operation-id-unique` to report.

- [FEATURE] QUERY and non-standard methods from `[AcceptVerbs]` (`[AcceptVerbs("QUERY")]`, `[AcceptVerbs("LINK")]`): OpenAPI 3.2 writes them as `query` and `additionalOperations.<METHOD>` (the key keeps the attribute's capitalization). For 3.0 and 3.1, which have no field for them, the serializer moves the whole operation into `x-oai-additionalOperations.<METHOD>`; each such operation now gets one warning (code `operation.moved-to-additional-operations`) located by the JSON pointer of the moved operation, since 3.0/3.1 tools do not see it. Warnings about an operation that was moved (such as a path+method conflict) are located there too.

- [FEATURE] Validation rules see every operation: any HTTP method (QUERY, TRACE, non-standard methods) in `paths` and operations in `webhooks` of standalone documents, with JSON pointers that follow the output of the validated version (`.../x-oai-additionalOperations/QUERY` for 3.0/3.1, `.../query` for 3.2, `#/webhooks/...`). `operation.operation-id-unique` also catches a duplicate between `paths` and `webhooks`. `path.params-match` and `parameter.path-required-true` stay on `paths` (they check path templates). Standalone `validate` of a 3.0/3.1 file still cannot see operations under `x-oai-additionalOperations`, because the OpenAPI reader does not load that extension back into operations.
- [BEHAVIOR] `--require-response-code` accepts `TRACE` and `QUERY`; the `safe` group is now GET, HEAD, OPTIONS, TRACE and QUERY, and `mutating` is every other method, including non-standard ones such as LINK (previously only POST, PUT, PATCH and DELETE).

- [FEATURE] Polymorphism, first case: an abstract base or an interface whose every derived type is declared with a discriminator value — `[JsonDerivedType(typeof(D), "value")]` or an integer value, with `[JsonPolymorphic(TypeDiscriminatorPropertyName = …)]` (default `$type`), or Swashbuckle's `[SwaggerDiscriminator]` + `[SwaggerSubType(…, DiscriminatorValue = …)]` — becomes a union component under the base's name: `oneOf` of variants `{Derived}As{Base}` plus `discriminator { propertyName, mapping }`. A variant is the derived type's properties plus the required discriminator property with its value (`const` for a string in 3.1/3.2, a one-element `enum` in 3.0 and for integers); the derived type's own component, used directly, has no discriminator, as on the wire. STJ attributes win over Swashbuckle ones. A base with a custom `[JsonConverter]` is left as before. A derived property serialized under the discriminator's name is an extraction error (exit 2), since System.Text.Json rejects that contract. References to the base are unchanged; OpenAPI 3.0 output changes only for such bases, which were previously flattened.

- [FEATURE] Polymorphism, remaining alternatives. A concrete base becomes a `oneOf` of its variants (including its own variant when the base is declared with a value) and a base branch `{Base}Default`: the base's properties, excluding every object a variant takes (no discriminator property at all, or with `IgnoreUnrecognizedTypeDiscriminators` a string or Int32 discriminator — the only values System.Text.Json reads — that is none of the mapped values). If some derived types are declared without a discriminator value the alternatives are not mutually exclusive: the union is `anyOf` (variants, the direct-use objects of the types without a value — `{Derived}Direct` when such a type is a polymorphic base of its own — and, for a concrete base, the base branch) without a `discriminator` object, with a warning that they are distinguishable only by structure. A warning also reports Swashbuckle polymorphism attributes that disagree with the System.Text.Json ones. Both are located at the union component and are not reported for unions reachable only from excluded paths; direct `SchemaGenerator` use reports them once per generator instance. Polymorphism configuration is not inherited: a union lists exactly the derived types its base declares. A base that lists itself without a value gets no extra alternative: the base branch describes it.

- [FEATURE] The `discriminator` object of a concrete polymorphic base depends on the target version. OpenAPI 3.2 gets `discriminator { propertyName, mapping, defaultMapping }` with `defaultMapping` on the base branch `{Base}Default`. OpenAPI 3.0 and 3.1 cannot express a discriminator whose property is optional, so the union is written as `oneOf` without a `discriminator` object, with one warning per union (code `polymorphism.discriminator-not-expressible`). Abstract bases and interfaces keep `discriminator { propertyName, mapping }` in every version; `anyOf` unions never get one. `UnknownDerivedTypeHandling` does not affect `defaultMapping`.

- [BUGFIX] Controller schemas no longer follow `ConfigureHttpJsonOptions`. ASP.NET Core serializes controller bodies with the MVC options (`AddControllers().AddJsonOptions(...)`) only, while `ConfigureHttpJsonOptions(...)` configures minimal APIs and `IResult`; the two sets were merged into one, so for example `ConfigureHttpJsonOptions` with `SnakeCaseLower` made controller schemas snake_case although controllers write camelCase. `JsonOptionsExtractionResult` gets `Mvc` and `Http` (`JsonContextOptions`, one per context); its flat properties keep the previous merged values and are marked `[Obsolete]`. `--naming-policy` / `OpenApiDocumentOptions.NamingPolicy` now applies only when Program.cs sets no JSON options in either context; a context Program.cs does not configure gets the ASP.NET Core default (camelCase). OpenAPI 3.0 output changes only for projects that configure JSON options through `ConfigureHttpJsonOptions` alone, or set some JSON option in Program.cs together with `--naming-policy`.

- [BUGFIX] The body type of a response follows the priority ASP.NET Core uses: the type declared for the status code (`[ProducesResponseType]`, `[SwaggerResponse]`), then for the 200 response the type of `[Produces(typeof(T))]` / `[Produces<T>]`, then the return type; the action wins over the controller at every level. Previously the type of `[Produces]` was ignored (only its content types were read), `[ProducesResponseType<T>]` and `[Produces<T>]` were not recognized at all, and a 200 declared without a type (`[ProducesResponseType(200)]` on `ActionResult<T>`) had no body. As in ApiExplorer, `[Produces(typeof(T))]` declares the 200 response, also next to other declared codes.
- [BUGFIX] `[ProducesResponseType]`, `[SwaggerResponse]`, `[ProducesDefaultResponseType]` and XML `<response>` on a controller class are read: they apply to every operation of the controller, and for one status code the action wins field by field (a type or description the action leaves open comes from the controller). As ApiExplorer does, an action whose controller declares responses no longer gets the 200 inferred from its return type. OpenAPI 3.0 output changes only for projects using these attributes or `<response>` on controllers, `[Produces]` with a type, the generic attribute forms, or a typeless `[ProducesResponseType(200)]` on a typed result.

- [BUGFIX] `IAsyncEnumerable<T>` responses (directly, inside `Task<>` / `ValueTask<>` / `ActionResult<>`, declared by a response attribute, or a user type implementing the interface) are described as what MVC writes: a JSON array, `type: array, items: T`. Previously they produced a fake object component such as `StreamItemIAsyncEnumerable`. Nullable elements give nullable items by the target version's rules: `Nullable<T>`, and a reference element annotated `T?` in the return type (`ActionResult<IAsyncEnumerable<Item?>>`, `Task<IAsyncEnumerable<string?>>`, …), also in the `itemSchema` of sequential media types; elements without annotations (`#nullable disable`) stay non-nullable. `IAsyncEnumerable<SseItem<T>>` from a controller is an array of `SseItem<T>` objects, as MVC writes it; server-sent events are never guessed from the type name.

- [FEATURE] An `IAsyncEnumerable<T>` response is described per declared media type. A sequential JSON media type (`application/jsonl`, `application/x-ndjson`, `application/json-seq`) gets `itemSchema: T` and no `schema` in OpenAPI 3.2; for 3.0 and 3.1 the serializer writes it as `x-oai-itemSchema`, with one warning per media type (code `media-type.item-schema-moved-to-extension`). `application/json` in the same response keeps the array. `text/event-stream` gets no schema and a warning in every version (code `response.event-stream-without-formatter`): standard MVC has no server-sent events formatter, so a custom one or `ServerSentEventsResult<T>` is needed. Global `[Produces]` filters get the same per-media-type form. `[Produces("text/event-stream")]` without a body type is unchanged.
- [BEHAVIOR] The warning unit is the topmost lost or moved node: a version warning located inside another one (for example the item schema of a QUERY operation that 3.0 moves into `x-oai-additionalOperations`) is not reported separately. Warnings about the input itself and component warnings (a component is a subtree of its own, also when reached only from a moved operation) are always reported.

- [BUGFIX] `ServerSentEventsResult<T>` responses are described as `text/event-stream` with the event schema of OpenAPI 3.2 as `itemSchema`: an object with a required string `data` (`contentMediaType: application/json`, `contentSchema: T`; a plain string for `string` and `byte[]`, which the result writes as is), string `event` and `id`, and an integer `retry` ≥ 0. For 3.0 and 3.1 the serializer writes `x-oai-itemSchema`, with one warning per media type. Previously such responses produced `application/json` with a fake component such as `StreamItemServerSentEventsResult`.
- [FEATURE] Server-sent events data is described by the HTTP JSON options (`ConfigureHttpJsonOptions`), as ASP.NET Core writes it. When those differ from the MVC options in naming policy, ignore condition, number handling or converters, a type used both by a controller body and by events data gets a second component for the HTTP context: `{Id}Http` (variants `{Derived}As{Id}Http` and the base branch `{Id}HttpDefault` of a polymorphic base follow, and the HTTP union refers only to HTTP components); a type used only by the HTTP context keeps its usual id. One warning (code `serialization-contexts.shared-types`) lists those types. The dictionary key policy does not split the contexts.

- [BUGFIX] Actions returning typed results are described by what the results write. `Results<…>` gives one response per variant; a framework result with a fixed status (`Ok<T>` 200, `Created<T>` 201, `Accepted<T>` 202, `NoContent` 204, `BadRequest<T>` 400, `ValidationProblem` 400 with `application/problem+json`, `UnauthorizedHttpResult` 401, `NotFound` 404, `Conflict` 409, `UnprocessableEntity` 422, `InternalServerError` 500, with or without a body) gives that status and its body, serialized with the HTTP JSON options; status-only results get no schema and no warning; explicit `[ProducesResponseType]` wins per status code, and `[Produces(typeof(T))]` / `[Produces<T>]` gives the 200 body ahead of the result's own value type. A result whose status is not statically known (untyped `IResult`, a user-defined result, `JsonHttpResult<T>`, `ProblemHttpResult`, …) gets a warning (code `response.result-status-unknown`) when the action declares no response; the known variants of a `Results<…>` that also contains such a result are still described, and only when no response is known at all a 200 response without a schema stands in. Previously these actions produced fake components such as `ResultItemOk`, `IResult` or `ResultItemOkAndNotFoundResults`. A body declared by an attribute on such an action is described in the HTTP context with the same streaming rules (`ServerSentEventsResult<T>`, `IAsyncEnumerable<T>` per media type). `ResponseInfo` gets `BodyFromHttpResult`.

- [BUGFIX] File content is described as raw bytes: MVC `FileResult` and its derived types (`FileStreamResult`, `FileContentResult`, …), `IFileHttpResult` results (`FileContentHttpResult`, `FileStreamHttpResult`, …), `Stream` and `IFormFile` become `type: string, format: binary` in every version (OpenAPI 3.1/3.2 keep this form, without `contentMediaType`), with no component for the framework type. A file response is written under its own declared media types, else `[Produces]`, else `application/octet-stream`; global `[Produces]` filters do not apply to it. Previously these types produced fake object components (`FileContentResult`, `Stream`, `IFormFile`, `EntityTagHeaderValue`, …) under `application/json`. OpenAPI 3.0 output changes for every API with file downloads or uploads.
- [BUGFIX] The media types of `[SwaggerResponse(code, description, typeof(T), contentTypes…)]` are the response's content keys; previously they were ignored and `application/json` was written. A global `[Produces]` filter no longer replaces media types that `[SwaggerResponse]` or `[ProducesResponseType(..., contentType)]` give the response itself.

- [BUGFIX] `[Consumes]` on an action or a controller sets the media types of the request body (the action wins over the controller, the controller over a global `[Consumes]` filter); previously a `[FromBody]` body was always `application/json`. A form body uses its `[Consumes]` media type (for example `application/x-www-form-urlencoded`) instead of always `multipart/form-data`, which stays the default.

- [FEATURE] Base64 data follows the target version: `byte[]` and `string` with `[Base64String]` are `type: string, format: byte` for OpenAPI 3.0 and `type: string, contentEncoding: base64` without `format` for 3.1 and 3.2 (`byte` is not in their format registry); nullable variants keep the version's nullable form. `[Base64String]` was ignored before. OpenAPI 3.0 output changes only for `[Base64String]` properties.

- [BUGFIX] A `[JsonExtensionData]` property (`IDictionary<string, object>`, `IDictionary<string, JsonElement>`, a type implementing one of them, or `JsonObject`; own or inherited, not `[JsonIgnore]`d) is no longer written as a normal property: it is left out of `properties` and `required`, and the object gets `additionalProperties: {}`, since System.Text.Json writes every extra member inline. A global unmapped-member `Disallow` yields to it, as in the serializer. Shapes System.Text.Json 10 rejects — another value or key type, two extension properties, an extension property bound to a constructor parameter, or `[JsonUnmappedMemberHandling(Disallow)]` on the same type — throw `OpenApiExtractionException` with the type and member (CLI exit 2).

- [BUGFIX] `[Range]` is translated exactly. `Range(Type, string, string)` read the `Type` as the minimum, so `[Range(typeof(decimal), "0.01", "999.99")]` became `maximum: 0.01`; its string bounds are now parsed in the invariant culture and written without passing through binary floating point (a 28-digit decimal keeps every digit). `MinimumIsExclusive` / `MaximumIsExclusive` give `exclusiveMinimum` / `exclusiveMaximum` (a number in 3.1/3.2; `minimum` + `exclusiveMinimum: true` in 3.0), independently per side. A declaration `RangeAttribute` itself rejects (minimum above maximum, equal bounds with an exclusive side, an unparseable string for a numeric operand, a NaN maximum) throws `OpenApiExtractionException` (CLI exit 2); a non-numeric operand type (`DateTime`) or a bound JSON cannot hold (infinity, an accepted NaN) gives a warning (code `schema.range-not-expressible`) and that bound is not written. Ranges apply only to numeric schemas; a `[Range]` on a property with a non-numeric schema no longer writes `minimum` / `maximum`.

- [FEATURE] Dictionary keys are constrained for OpenAPI 3.1 and 3.2 with `propertyNames`, never narrower than what System.Text.Json 10 writes and accepts: `Guid` keys `{type: string, format: uuid}`, signed integer keys `^[+-]?[0-9]+$`, unsigned ones `^\+?[0-9]+$` (leading zeros allowed; the type's range is not clamped). String and enum keys, and keys of a type with a converter of its own, stay unconstrained; a converter unknown to the extractor (on the key type, or registered globally for `Guid` / integer keys) gives a warning (code `schema.unknown-key-converter`). OpenAPI 3.0 has no such keyword and is unchanged, without a warning. Key and value types are taken from the dictionary interface the type implements, not from the position of its own generic arguments.
- [BUGFIX] `[MinLength]` / `[MaxLength]` on a dictionary give `minProperties` / `maxProperties` instead of `minLength` / `maxLength`.

- [FEATURE] `[AllowedValues]` gives `enum` with values of the schema's JSON type (numbers stay numbers; a single string value is `const` for 3.1/3.2, a one-element `enum` otherwise) and `[DeniedValues]` gives `not: {enum: [...]}`. They combine with the schema's own constraints by AND: next to other keywords as siblings; on an enum type, whose own `enum` is kept, and on a reference, as a separate `allOf` element — no intersection is computed. Values that are not of the property's JSON type give a warning (code `schema.value-not-convertible`) and no constraint. Both attributes were ignored before.

- [BUGFIX] Number handling follows what System.Text.Json 10 writes and reads. `[JsonNumberHandling]` on a property or type is read (property over type over the global option; `Strict` on a property switches the global string flags off); it was ignored. `AllowReadingFromString`, `WriteAsString` or both give `anyOf: [number, numeric string]` — previously `WriteAsString` gave `{type: string}` only, although a JSON number is read. The numeric string is `^[+-]?[0-9]+$` for integers and an optional sign, digits with an optional fraction (`.5`, `1.`) and exponent for `float` / `double` / `decimal` / `Half` (for `Half` also surrounding white space and group separators, which STJ accepts). For `float` / `double` / `Half` any of the three flags adds `enum: ["NaN", "Infinity", "-Infinity"]`. Ranges constrain the numeric branch only; a nullable number puts `nullable: true` on the union (3.0) or adds a `null` branch (3.1/3.2); collections apply the rule to their items. `Half` is now a number (`format: float`), and `uint` has `format: int64`, since its values exceed `int32`.

## [0.16.1] - 2026-10-07

- [DOCS] README "Why" section corrected. It claimed that `swagger tofile` and `Microsoft.AspNetCore.OpenApi` need the application to fully start with real infrastructure. In fact both run the app's startup code (Microsoft's build-time generator invokes the entry point with a mock server; the Swashbuckle CLI builds the app's host), so they fail only when that startup code itself needs a database, broker, external API or a required environment variable, and both offer documented guards (`GetDocument.Insider`, `SwaggerHostFactory`). No code changes.

## [0.16.0] - 2026-10-07

- [SECURITY] `Microsoft.OpenApi` and `Microsoft.OpenApi.YamlReader` bumped 3.5.0 → 3.10.2. Fixes two high-severity denial-of-service advisories, both reachable through the `validate` command, which parses user-supplied spec files in-process:
  - [GHSA-v5pm-xwqc-g5wc](https://github.com/advisories/GHSA-v5pm-xwqc-g5wc) (CVE-2026-49451): a document with circular schema references caused uncontrolled recursion and terminated the process. Fixed in `Microsoft.OpenApi` 3.5.4.
  - [GHSA-7pxr-59rr-hqj2](https://github.com/microsoft/OpenAPI.NET/security/advisories/GHSA-7pxr-59rr-hqj2) (CVE-2026-72923): a small YAML document with nested anchors and aliases caused unbounded expansion and out-of-memory termination. Fixed in `Microsoft.OpenApi.YamlReader` 3.10.0.
- [BEHAVIOR] OpenAPI 3.0 output (the default `--openapi-version`) changes for nullable properties typed as another component schema. The upstream serializer now emits the null branch inside the composite instead of a sibling `nullable` flag (Microsoft.OpenApi 3.9.0 moved the null branch into the composite, "handle nullability more accurately during serialization for 3.0"; 3.10.0 added `nullable: true` on that branch, "better nullability round-tripping"):
  - before: `{"anyOf": [{"$ref": "#/components/schemas/UserDto"}], "nullable": true}`
  - after: `{"anyOf": [{"$ref": "#/components/schemas/UserDto"}, {"enum": [null], "nullable": true}]}`

  OpenAPI 3.1 and 3.2 output is unchanged. If you generate client SDKs from 3.0 specs, regenerate and review nullable reference properties.
- [BUGFIX] `Program.cs` analysis: in-project `const string` names now resolve to their literal value, as the README promises. Previously `c.AddSecurityDefinition(Consts.SchemeName, ...)` printed `Warning: AddSecurityDefinition call with non-literal name — skipped.` and the scheme was missing from `components/securitySchemes`; the same happened to `Response.Headers.Append/Add/TryAdd(Consts.X, ...)` and `Response.Headers[Consts.X] = ...` in middleware (header dropped with a warning), and `AddJwtBearer(Consts.X, ...)` silently fell back to the default scheme name `Bearer`. Cause: `SourceCompiler` referenced only the `System.Runtime` / `mscorlib` / `netstandard` facades from the runtime directory, which type-forward `System.Object` and `System.String` to `System.Private.CoreLib`, but not `System.Private.CoreLib` itself — the compilation had no core library, `string` did not bind, and `SemanticModel.GetConstantValue` returned no value. The fix adds the core library (`typeof(object).Assembly.Location`) to the compilation's references. Scheme names inside `AddSecurityRequirement` had the same gap for a different reason: `SecuritySchemeExtractor` read them from string literals only and never consulted the semantic model, so `new OpenApiSecuritySchemeReference(Consts.X)` (Microsoft.OpenApi 2.x+, including the `doc => ... (Consts.X, doc)` lambda-factory form) and `new OpenApiReference { Id = Consts.X, Type = ReferenceType.SecurityScheme }` (1.x) were dropped without a warning, leaving the document without a global security requirement. Both patterns now resolve in-project constants through the same `GetConstantValue` path; a scheme name that is neither a literal nor a constant is reported with `Warning: AddSecurityRequirement call with non-literal scheme name — skipped.` instead of being dropped silently. Specs of projects that use only string literals are unchanged.
- [BUGFIX] Security requirements are now written to the spec file, with the correct OR/AND structure. Previously every `security` requirement the tool produced — document-level from `AddSecurityRequirement` and per-operation from `[Authorize(AuthenticationSchemes = ...)]` — was serialized as an empty object, `security: [{}]`, even when the scheme was declared in `components/securitySchemes`. An empty requirement means "no authentication required", so SDK clients generated from the spec never sent credentials. The requirements were correct in memory (and visible to `--validate`), but `OpenApiDocumentBuilder` created each `OpenApiSecuritySchemeReference` without a host document, and Microsoft.OpenApi writes a requirement key only if the reference resolves against its host document's `components/securitySchemes`. The builder now passes the document being built as the host document, so a requirement on a declared scheme is written as `{"ApiKey": []}`. Document-level requirements also had the wrong logic: the names from all `AddSecurityRequirement` calls were merged into one requirement object, whose keys OpenAPI reads as AND, so two calls for `ApiKey` and `Bearer` (either scheme suffices) came out as "both are required". Each call now yields its own requirement object — `[{"ApiKey": []}, {"Bearer": []}]` (OR) — while several names inside one call stay in one object (AND). For the public `SecuritySchemeExtractionResult` this adds `GlobalRequirements` (one name list per call); `GlobalRequirementSchemeNames` is marked `[Obsolete]` — it flattens the groups — and still works (reading returns all names, setting it creates a single combined requirement as before). Only the `referenceId` argument of `new OpenApiSecuritySchemeReference(...)` is now read as a scheme name; previously any string literal argument, such as an `externalResource` URI, was taken as one too. A requirement naming a scheme that is not declared in `components/securitySchemes` (for example `[Authorize(AuthenticationSchemes = "Bearer")]` without a matching `AddJwtBearer` / `AddSecurityDefinition`) can't be written validly — OpenAPI requires every name to be a declared scheme — and was previously also written as `{}`. Such a name is now omitted with `Warning: security requirement references undeclared scheme 'Bearer' (GET /api/secure/admin) — omitted; declare it with AddSecurityDefinition.` (or `(document-level)`). Declared names in the same requirement are kept. A requirement left without names is dropped, and an operation left without requirements gets no `security` key, so it inherits the document-level requirement instead of claiming anonymous access. `[AllowAnonymous]` still writes `security: []`, which removes the document-level requirement for that operation.
- [DEPS] `System.CommandLine` 2.0.5 → 2.0.12, `System.Reflection.MetadataLoadContext` 10.0.5 → 10.0.12.

## [0.12.0] - 2026-04-30

- [BUGFIX] XML doc descriptions for types and properties declared as nested types (e.g. `public class FooController { public class ServiceDto { ... } }`) now resolve correctly. Reflection emits nested types with a `+` separator in `FullName` (e.g. `Namespace.FooController+ServiceDto`), while the C# XML compiler emits keys with a `.` separator (`T:Namespace.FooController.ServiceDto`). The dictionary lookup in `XmlDocParser` always missed for every nested type, silently dropping all `T:`, `P:`, `F:`, and `M:` entries. The fix introduces a private `NormalizeTypeName` helper that replaces `+` with `.` before constructing lookup keys; it is applied consistently across `GetTypeDoc`, `GetPropertyDoc`, `GetFieldDoc`, `BuildMethodKey`, and `GetXmlTypeName` (including the generic-definition and parameter-type paths inside those methods).
- [BUGFIX] Property descriptions declared on a base class (e.g. `<summary>` on `ServerRequestBase.Host`) now propagate to schemas for derived types (e.g. `CreateServerRequest`). The XML doc key for an inherited property lives under the declaring (base) type — `P:Namespace.ServerRequestBase.Host` — but `DocumentationResolver.ResolveProperty` previously looked up the key using the leaf (derived) type, which always missed. The fix uses `property.DeclaringType` as the XML lookup key — which is the base type for inherited properties and the most-derived type for overridden properties — so both cases resolve correctly through a single lookup without any fallback chain. Note: this does not resolve `<inheritdoc/>` tags — the C# compiler does not inline inherited XML at compile time, so `<inheritdoc/>`-only members will still produce no description.

## [0.11.0] - 2026-04-29

- [BUGFIX] Default-target attributes on positional record primary-constructor parameters now reach the schema. Given `public record CreateRequest([Required, StringLength(100)] string Name)`, the C# compiler emits `[Required]` and `[StringLength]` onto the constructor `ParameterInfo` — never onto the synthesized `PropertyInfo`. The extractor previously read only `propInfo.GetCustomAttributesData()` and silently emitted a property schema with no validation. The fix walks the declaring type's instance constructors (public + non-public, so `internal record` works), finds the parameter whose name matches the property, and merges its attributes with the property's own. Type-match (`ParameterInfo.ParameterType.FullName == PropertyInfo.PropertyType.FullName`) is used as a tiebreaker when a secondary user-written constructor reuses the same parameter name. Explicit `[property: ...]` and `[param: ...]` targets continue to work; the merge is additive. The same fix applies to C# 12 primary-constructor classes whose properties mirror primary-ctor parameter names by convention. JSON attributes that forbid `Parameter` in their `AttributeUsage` (`[JsonPropertyName]`, `[JsonIgnore]`) still require explicit `[property: ...]` — the C# compiler rejects them on positional record parameters with CS0592.
