# Changelog

All notable changes to this project.

## [Unreleased]

### Changes to OpenAPI 3.0 output

OpenAPI 3.0 stays the default target. A project that uses none of the constructs below gets the same 3.0 document as with 0.16. In particular these do not change: `format: byte` for `byte[]`, the nullable form of 0.16.0, the `allOf` wrapper of reference-typed properties, the `operationId` of single-method actions, server URLs, and the AND/OR structure of security requirements (except where a `mutualTLS` scheme is removed). Each item below is listed in detail further down; the impact on generated SDKs is given for each.

**Operations**

- Actions declared with `[AcceptVerbs]`, or with a subclass of a built-in `[Http*]` attribute, appear; they were silently dropped. *SDK:* new methods.
- Several actions on one path and method: the document keeps the action chosen by an ordinal key (controller type, method name, parameter types, attribute order) instead of the last one discovered. *SDK:* the method may now describe a different action.
- The `operationId` of a multi-method action comes from the `Name` of the attribute that produced each operation; previously the first `Name` was used for all of them. *SDK:* method names of such actions may change.
- QUERY and non-standard methods (`[AcceptVerbs("QUERY")]`) are written under `x-oai-additionalOperations`, with a warning; 3.0 tools do not see them.
- Operations whose `[Authorize(Roles)]` inherit the document's security requirements get those requirements written on the operation (the role values themselves exist only in 3.1/3.2). *SDK:* no change in the authentication used.

**Responses and bodies**

- `IAsyncEnumerable<T>` responses are `type: array, items: T` (nullable items for `Nullable<T>` and annotated `T?` elements); a declared sequential media type (`application/x-ndjson`, `application/jsonl`, `application/json-seq`) gets its item schema as `x-oai-itemSchema`; `ServerSentEventsResult<T>` is `text/event-stream` with the event schema in `x-oai-itemSchema`. The fake components (`StreamItemIAsyncEnumerable`, `StreamItemServerSentEventsResult`, …) disappear. *SDK:* streaming endpoints return a list (or an untyped stream) instead of a non-existent wrapper class; code that referenced the wrapper must change.
- Typed results (`Results<…>`, `Ok<T>`, `Created<T>`, `NotFound`, …) give one response per status with its real body; the fake components (`ResultItemOk`, `IResult`, `ResultItemOkAndNotFoundResults`, …) disappear. *SDK:* response types become the payload types; error statuses appear.
- File content (`FileResult` and derived types, `IFileHttpResult`, `Stream`, `IFormFile`) is `type: string, format: binary` under the declared media type (default `application/octet-stream`); the fake object components disappear. *SDK:* downloads and uploads become binary streams / byte arrays instead of objects.
- The 200 body type follows `[Produces(typeof(T))]` / `[Produces<T>]`; `[ProducesResponseType<T>]` and `[Produces<T>]` are recognized; a typeless `[ProducesResponseType(200)]` takes the return type; `[ProducesResponseType]`, `[SwaggerResponse]`, `[ProducesDefaultResponseType]` and XML `<response>` on a controller apply to its operations (and an action whose controller declares responses no longer gets the inferred 200). *SDK:* response types and documented statuses change for these actions.
- `[Consumes]` sets the request body media types; a form body uses its `[Consumes]` media type; `[SwaggerResponse(…, contentTypes)]` sets the response media types, and a global `[Produces]` filter no longer replaces the media types a response gets from `[SwaggerResponse]` or `[ProducesResponseType(…, contentType)]`. *SDK:* clients send and accept the media types the server really uses.
- Controller schemas follow only the MVC JSON options (`AddJsonOptions`), not `ConfigureHttpJsonOptions`; `--naming-policy` applies only when Program.cs sets no JSON options at all; when the MVC and HTTP options differ, a type used by both a controller and an HTTP-context body (typed results, event data) gets a second component `{Id}Http`. *SDK:* property names match the wire again; some types get a second model class.
- JSON options set in an expression-bodied lambda (`AddJsonOptions(o => …)`) are read. *SDK:* naming, number handling and enum converters configured that way now apply.

**Schemas**

- Two closed generic types whose component id collided (`A.Page<Item>` and `B.Page<Item>`) no longer share one component: the second gets a full-name fallback id. *SDK:* a second model class appears where one wrongly served both.
- Polymorphic bases (`[JsonPolymorphic]` / `[JsonDerivedType]`, or `[SwaggerDiscriminator]` / `[SwaggerSubType]`) become union components under the base's name: `oneOf` (or `anyOf` when some derived types have no discriminator value) of variants `{Derived}As{Base}`, the base branch `{Base}Default` for a concrete base and `{Derived}Direct` for a derived type that is a base of its own; abstract bases and interfaces get `discriminator { propertyName, mapping }`, a concrete base gets no `discriminator` object in 3.0 (with a warning). References to the base keep their target. *SDK:* inheritance hierarchies instead of flattened classes; new variant classes.
- A `[JsonExtensionData]` property leaves `properties` and the object gets `additionalProperties: {}`. *SDK:* the extension dictionary is no longer a regular property.
- `object` and `dynamic` properties are `{}` instead of `type: object`. *SDK:* such properties accept any JSON value.
- camelCase names that start with an acronym follow System.Text.Json (`IOStatus` → `ioStatus`, previously `iOStatus`), for properties and for enum members under a camelCase converter. *SDK:* such properties deserialize again; their generated names may change.
- Enum values are the names the converter in force writes: `[JsonStringEnumMemberName]` for System.Text.Json, `[EnumMember(Value)]` for Newtonsoft, the naming policy of a global string-enum converter (`new JsonStringEnumConverter(JsonNamingPolicy.CamelCase)`, Newtonsoft naming strategies), which wins over `[JsonConverter]` on the enum type as in System.Text.Json; a converter on a `Nullable<TEnum>` property makes it a string enum. `x-enum-varnames` keeps the CLR names; `x-enum-varnames` and `x-enum-descriptions` now also appear on an enum whose string converter is on the property, which had neither. *SDK:* enum wire values match the server; such enums get member names and descriptions.
- Enums backed by `long` / `ulong` keep their values instead of truncating them to `int`, with the `type` / `format` of their underlying type. *SDK:* 64-bit enum values are representable.
- Number handling follows System.Text.Json: `[JsonNumberHandling]` on a property or type is read, and `AllowReadingFromString` / `WriteAsString` give `anyOf: [number, numeric string]` (`NaN`/`Infinity` names for floating point) instead of a plain number or `{type: string}`; `Half` is a number (`format: float`), `uint` has `format: int64` and `ulong` has no `format`. *SDK:* such properties become union types or wider integer types.
- `[Range]` is exact: `Range(Type, "min", "max")` gives its real bounds (it wrote the type as the minimum), bounds are printed without passing through binary floating point (a 28-digit decimal keeps every digit, a `float` or `Half` bound is `0.1` rather than `0.10000000149011612`), exclusive sides give `exclusiveMinimum` / `exclusiveMaximum` (`minimum` + `exclusiveMinimum: true` in 3.0), and `[Range]` on a non-numeric schema writes nothing. *SDK:* client-side validation follows the real bounds.
- `[AllowedValues]` gives `enum` and `[DeniedValues]` gives `not: {enum}`.
- `[Length]`, `[DataType]` (format), `[Display(Description)]`, `[ReadOnly(true)]` and `[SwaggerSchema]` `ReadOnly` / `WriteOnly` / `Title` / `Format` are read; `[MinLength]` / `[MaxLength]` on a dictionary give `minProperties` / `maxProperties`; several length attributes keep the tighter bound. The format has one winner (`[SwaggerSchema(Format)]` → `[EmailAddress]` / `[Url]` / `[Phone]` → `[DataType]` → the type), so these attributes now replace a type's format; the description has `[SwaggerSchema(Description)]` (also as the constructor argument) above `[Description]`, and either of them above the default description of a well-known converter; an XML `<summary>` (or record `<param>`) of the property wins over all of these attributes, as in Swashbuckle at run time, so a property with both keeps its 0.16 XML description where 0.16 already preferred XML (`[SwaggerSchema]` constructor form, `[Display(Description)]`) and now gets the XML text instead of the attribute where 0.16 preferred the attribute (named `[SwaggerSchema(Description)]`, `[Description]`). *SDK:* read-only/write-only members and formats (`date`, `email`, …) map to other types or annotations.
- `[Base64String]` strings get `format: byte`, as `byte[]` already did.
- XML `<example>` on DTO properties and types is written as `example`; XML `<param example="…">` gives parameter and request body examples. *SDK:* documentation only.
- `[DefaultValue(typeof(T), "…")]` writes the converted value instead of the type name; numeric literal defaults on properties (`[DefaultValue((byte)5)]`, …) are numbers instead of strings, as they already were on parameters of `int`, `long` and floating-point types; on parameters of `byte`, `sbyte`, `short`, `ushort`, `uint` and `ulong` a C# default or `[DefaultValue]` is a number instead of an empty `default:`, which made the JSON document unparseable; enum defaults (also C# defaults of enum parameters) use the enum's wire form. *SDK:* default values get the property's type.

**Parameters**

- Validation attributes on action parameters (`[Range]`, `[StringLength]`, `[MinLength]`, `[MaxLength]`, `[Length]`, `[RegularExpression]`, `[AllowedValues]`, `[DeniedValues]`, format attributes) apply to path, query and header parameters, to form fields and to the `[FromBody]` schema; the synthetic form object lists its required fields in `required`. *SDK:* client-side validation of parameters; form fields marked required.
- `[FromForm(Name = …)]` renames the form field; the XML `<param>` description of a parameter renamed with `[FromQuery/FromHeader/FromRoute(Name = …)]` is kept; `[SwaggerParameter(Required = …)]` sets `required`. *SDK:* form field names match the wire.
- `[SwaggerTag(description, externalDocsUrl)]` gives the controller's tag `externalDocs`.

**Security**

- OAuth2 and OpenID Connect schemes from `AddSecurityDefinition` are written with their flows, URLs and scopes (the build used to fail on them), and requirement scopes are written instead of `[]`; the OpenAPI 3.2 security fields, when set (`OAuth2MetadataUrl`, `Deprecated`, the `DeviceAuthorization` flow), become `x-oai-oauth2-metadata-url`, `x-oai-deprecated` and `x-oai-deviceAuthorization` with a warning. *SDK:* OAuth2 clients get their flows and scopes.
- A `mutualTLS` scheme, which OpenAPI 3.0 cannot express, is removed together with its name in every requirement, with a warning listing the changed requirements; it was dropped silently before, now its requirements change. *SDK:* operations that required only mutual TLS show no security requirement in 3.0.

**Document metadata.** `OpenApiInfo { License = new OpenApiLicense { Name, Url } }` in `SwaggerDoc` / `AddOpenApi` of Program.cs is read (also in the target-typed form `new() { License = new() { … } }`, as are target-typed tags, external docs, security definitions and requirement references, which were skipped silently), so `info.license` appears in 3.0 for projects that declare it there (CLI license flags still win field by field). New sources and flags of OpenAPI 3.1/3.2 fields (`info.summary`, `license.identifier`, `servers[].name`, `$self`, `jsonSchemaDialect`, tag `summary` / `parent` / `kind`) change a 3.0 document only when they are set: they become `x-oai-*` / `x-oas-*` extensions or are omitted, each with a warning. `$self` (`x-oai-$self` in 3.0) is written exactly as given, percent-encodings included.

### Exit codes

The values are unchanged (0 success, 1 validation errors, 2 errors), but some runs that used to exit with 0 now exit with 2:

- annotations that are provably wrong: a `[Range]` that `RangeAttribute` itself rejects, a `[JsonExtensionData]` shape System.Text.Json rejects, a derived property named like the discriminator, a property both read-only and write-only, a literal OAuth2 / OpenID Connect declaration without the flows or URLs OpenAPI requires (`OpenApiExtractionException`);
- conflicting configuration: a license identifier together with a URL, a license URL or identifier without a name (the license used to be dropped silently), a number of server names different from the number of servers, an empty or repeated server name, a malformed `$self`, a dialect that is not the base dialect of the target version (`OpenApiConfigurationException`). Library callers also get `OpenApiConfigurationException` for a target version other than 3.0, 3.1 or 3.2 and for a `ValidationContext.OpenApiSpecVersion` that differs from the build version.

With `--validate`, the new validation rules can turn a passing run into exit 1: a 3.1/3.2 license with both an identifier and a URL, a document without `paths` (3.0) or without any of `paths` / `webhooks` / `components` (3.1/3.2), a 3.2 tag with an undeclared parent or a parent cycle, two 3.2 servers with one name, a 3.2 discriminator with an optional property and no `defaultMapping`. In the other direction, a missing response description is only a warning for 3.2, and the response, constraint, format and unused-component rules no longer report the tool's own output.

### All changes

- [FEATURE] The target OpenAPI version is a build option on every public Core surface: `OpenApiDocumentOptions.OpenApiVersion` and `SchemaOptions.OpenApiVersion` (`Microsoft.OpenApi.OpenApiSpecVersion`, default `OpenApi3_0`). A document is built for that version and is supported only when serialized into the same version. The CLI parses `--openapi-version` once and uses the value for the build, the validation and the serialization. Output does not change yet: the option is the carrier for version-dependent forms.
- [BEHAVIOR] A version other than 3.0, 3.1 or 3.2 (`OpenApi2_0`, or a value outside the enum) makes `OpenApiDocumentBuilder.Build`, `OpenApiDocumentBuilder.BuildWithValidation` and `new SchemaGenerator(...)` throw the new public `OpenApiConfigurationException` (derived from `InvalidOperationException`) before the assembly is loaded. `BuildWithValidation` takes the validation version from the build options when `ValidationContext.OpenApiSpecVersion` is `null`; an explicit value that differs from `OpenApiDocumentOptions.OpenApiVersion` now throws `OpenApiConfigurationException`. Library callers that set `ValidationContext.OpenApiSpecVersion` to 3.1 or 3.2 must set the same `OpenApiVersion` in the build options. The CLI exit code for an unknown `--openapi-version` stays 2.

- [FEATURE] Public diagnostics channel. Warnings produced while extracting are now `ExtractionDiagnostic` records (`Code` from `ExtractionDiagnosticCodes`, `Message`, `Location`, `Subjects` and, for version-related warnings, `TargetVersion`, `Feature`, `Action`, `ExtensionName`, `RequiredVersion`), delivered to `OpenApiDocumentOptions.OnDiagnostic` or `SchemaOptions.OnDiagnostic`. Library callers no longer need to capture `Console.Error`. Without a subscriber every warning is printed to stderr with its previous text, so CLI output is unchanged. The public extractors (`SecuritySchemeExtractor`, `JsonOptionsExtractor`, `PathBaseExtractor`, `ResponseHeaderExtractor`, `GlobalMediaTypesExtractor`) get overloads taking an `Action<ExtractionDiagnostic>?`; the existing signatures still print to stderr.
- [BEHAVIOR] Within one build, a warning repeated with the same code, place and text is reported once (for direct schema generation: once per `SchemaGenerator` instance). Previously, for example, a security scheme registered three times printed the duplicate warning twice.
- [FEATURE] New public `OpenApiExtractionException` (derived from `InvalidOperationException`, with `TypeName` and `MemberName`) for annotations that are provably wrong; it is not raised yet.

- [BUGFIX] Two different closed generic types whose component id came out the same — for example `A.Page<Item>` and `B.Page<Item>`, both `ItemPage` — silently shared one component, so the second response was described by the first type's schema. Every component id is now reserved per CLR type: the second type gets the fallback id (`Item` + the full name of its generic definition with `.`/`+` → `_`, e.g. `ItemB_Page`), and a numeric suffix if that is taken too. Ids that did not collide are unchanged, including the existing full-name fallback for two non-generic types with one short name. OpenAPI 3.0 output changes only for documents that had such a collision.

- [FEATURE] With the OpenAPI 3.0 target, a GET, HEAD or DELETE operation that has a request body now gets one warning naming the method and path: OpenAPI 3.0 supports `requestBody` only on methods whose HTTP semantics define a body, so 3.0 consumers must ignore it. The output is unchanged; 3.1 and 3.2 targets, where such a body is allowed, get no warning. Warnings of this kind are delivered after the document is final, so operations on excluded paths are never reported, and their order is deterministic.

- [BUGFIX] Actions declared with `[AcceptVerbs]` are no longer lost. Each method of `[AcceptVerbs("GET", "POST")]` or `[AcceptVerbs("PUT")]` becomes an operation on the attribute's `Route`, and methods from `[AcceptVerbs]` and `[Http*]` on one action are united without duplicates. An empty `[AcceptVerbs()]`, or a custom attribute derived from `HttpMethodAttribute` whose methods are not visible in metadata, skips the action with a warning instead of guessing a method from the attribute's name; a subclass of a built-in `[Http*]` attribute keeps that attribute's method. `ActionDiscovery.DiscoverActions` gets overloads with an `onDiagnostic` callback, and `ActionInfo` gets `OperationName` (the attribute's `Name`) and `AttributeOrder`. OpenAPI 3.0 output changes only for projects that use `[AcceptVerbs]` or such subclasses: the operations appear.

- [BUGFIX] When several actions declare the same path and HTTP method, the document keeps one chosen by an ordinal key — controller type full name, action method name, parameter type full names (overloads), attribute order in metadata — instead of the last one discovered, and a warning names every action involved. `--validate` locations point at the same winning action (previously at the first one discovered, while the document showed the last). Operations on excluded paths are not reported. OpenAPI 3.0 output changes only where such a conflict exists.
- [BEHAVIOR] An operation's `operationId` falls back to the `Name` of the attribute that produced that operation (`[HttpGet(Name = …)]`, `[AcceptVerbs(…, Name = …)]`). Previously the first `Name` found on any `[Http*]` attribute of the method was used for every operation of the method. When one action declares the same method and route twice (`[HttpGet(Name = …)]` and `[AcceptVerbs]`), the first given `Name` is kept; two different names keep the first with a warning. No id is ever synthesized; an explicit `[SwaggerOperation(OperationId)]` is shared by all operations of a multi-method action and left for `operation.operation-id-unique` to report.

- [FEATURE] QUERY and non-standard methods from `[AcceptVerbs]` (`[AcceptVerbs("QUERY")]`, `[AcceptVerbs("LINK")]`): OpenAPI 3.2 writes them as `query` and `additionalOperations.<METHOD>` (the key keeps the attribute's capitalization). For 3.0 and 3.1, which have no field for them, the serializer moves the whole operation into `x-oai-additionalOperations.<METHOD>`; each such operation now gets one warning (code `operation.moved-to-additional-operations`) located by the JSON pointer of the moved operation, since 3.0/3.1 tools do not see it. Warnings about an operation that was moved (such as a path+method conflict) are located there too.

- [FEATURE] Validation rules see every operation: any HTTP method (QUERY, TRACE, non-standard methods) in `paths` and operations in `webhooks` of standalone documents, with JSON pointers that follow the output of the validated version (`.../x-oai-additionalOperations/QUERY` for 3.0/3.1, `.../query` for 3.2, `#/webhooks/...`). `operation.operation-id-unique` also catches a duplicate between `paths` and `webhooks`. `path.params-match` and `parameter.path-required-true` stay on `paths` (they check path templates). Standalone `validate` of a 3.0/3.1 file still cannot see operations under `x-oai-additionalOperations`, because the OpenAPI reader does not load that extension back into operations.
- [BEHAVIOR] `--require-response-code` accepts `TRACE` and `QUERY`; the `safe` group is now GET, HEAD, OPTIONS, TRACE and QUERY, and `mutating` is every other method, including non-standard ones such as LINK (previously only POST, PUT, PATCH and DELETE).

- [FEATURE] Polymorphism, first case: an abstract base or an interface whose every derived type is declared with a discriminator value — `[JsonDerivedType(typeof(D), "value")]` or an integer value, with `[JsonPolymorphic(TypeDiscriminatorPropertyName = …)]` (default `$type`), or Swashbuckle's `[SwaggerDiscriminator]` + `[SwaggerSubType(…, DiscriminatorValue = …)]` — becomes a union component under the base's name: `oneOf` of variants `{Derived}As{Base}` plus `discriminator { propertyName, mapping }`. A variant is the derived type's properties plus the required discriminator property with its value (`const` for a string in 3.1/3.2, a one-element `enum` in 3.0 and for integers); the derived type's own component, used directly, has no discriminator, as on the wire. STJ attributes win over Swashbuckle ones. A base with a custom `[JsonConverter]` is left as before. A derived property serialized under the discriminator's name is an extraction error (exit 2), since System.Text.Json rejects that contract. References to the base are unchanged; OpenAPI 3.0 output changes only for such bases, which were previously flattened.

- [FEATURE] Polymorphism, remaining alternatives. A concrete base becomes a `oneOf` of its variants (including its own variant when the base is declared with a value) and a base branch `{Base}Default`: the base's properties, excluding every object a variant takes (no discriminator property at all, or with `IgnoreUnrecognizedTypeDiscriminators` a string or Int32 discriminator — the only values System.Text.Json reads — that is none of the mapped values). If some derived types are declared without a discriminator value the alternatives are not mutually exclusive: the union is `anyOf` (variants, the direct-use objects of the types without a value — `{Derived}Direct` when such a type is a polymorphic base of its own — and, for a concrete base, the base branch) without a `discriminator` object, with a warning that they are distinguishable only by structure. A warning also reports Swashbuckle polymorphism attributes that disagree with the System.Text.Json ones. Both are located at the union component and are not reported for unions reachable only from excluded paths; direct `SchemaGenerator` use reports them once per generator instance. Polymorphism configuration is not inherited: a union lists exactly the derived types its base declares. A base that lists itself without a value gets no extra alternative: the base branch describes it.

- [FEATURE] The `discriminator` object of a concrete polymorphic base depends on the target version. OpenAPI 3.2 gets `discriminator { propertyName, mapping, defaultMapping }` with `defaultMapping` on the base branch `{Base}Default`. OpenAPI 3.0 and 3.1 cannot express a discriminator whose property is optional, so the union is written as `oneOf` without a `discriminator` object, with one warning per union (code `polymorphism.discriminator-not-expressible`). Abstract bases and interfaces keep `discriminator { propertyName, mapping }` in every version; `anyOf` unions never get one. `UnknownDerivedTypeHandling` does not affect `defaultMapping`.

- [BUGFIX] Controller schemas no longer follow `ConfigureHttpJsonOptions`. ASP.NET Core serializes controller bodies with the MVC options (`AddControllers().AddJsonOptions(...)`) only, while `ConfigureHttpJsonOptions(...)` configures minimal APIs and `IResult`; the two sets were merged into one, so for example `ConfigureHttpJsonOptions` with `SnakeCaseLower` made controller schemas snake_case although controllers write camelCase. `JsonOptionsExtractionResult` gets `Mvc` and `Http` (`JsonContextOptions`, one per context); its flat properties keep the previous merged values and are marked `[Obsolete]`. `--naming-policy` / `OpenApiDocumentOptions.NamingPolicy` now applies only when Program.cs sets no JSON options in either context; a context Program.cs does not configure gets the ASP.NET Core default (camelCase). OpenAPI 3.0 output changes only for projects that configure JSON options through `ConfigureHttpJsonOptions` alone, or set some JSON option in Program.cs together with `--naming-policy`.

- [BUGFIX] The body type of a response follows the priority ASP.NET Core uses: the type declared for the status code (`[ProducesResponseType]`, `[SwaggerResponse]`), then for the 200 response the type of `[Produces(typeof(T))]` / `[Produces<T>]`, then the return type; the action wins over the controller at every level. Previously the type of `[Produces]` was ignored (only its content types were read), `[ProducesResponseType<T>]` and `[Produces<T>]` were not recognized at all, and a 200 declared without a type (`[ProducesResponseType(200)]` on `ActionResult<T>`) had no body. As in ApiExplorer, `[Produces(typeof(T))]` declares the 200 response, also next to other declared codes.
- [BUGFIX] `[ProducesResponseType]`, `[SwaggerResponse]`, `[ProducesDefaultResponseType]` and XML `<response>` on a controller class are read: they apply to every operation of the controller, and for one status code the action wins field by field (a type or description the action leaves open comes from the controller). As ApiExplorer does, an action whose controller declares responses no longer gets the 200 inferred from its return type. OpenAPI 3.0 output changes only for projects using these attributes or `<response>` on controllers, `[Produces]` with a type, the generic attribute forms, or a typeless `[ProducesResponseType(200)]` on a typed result.

- [BUGFIX] `IAsyncEnumerable<T>` responses (directly, inside `Task<>` / `ValueTask<>` / `ActionResult<>`, declared by a response attribute, or a user type implementing the interface) are described as what MVC writes: a JSON array, `type: array, items: T`. Previously they produced a fake object component such as `StreamItemIAsyncEnumerable`. Nullable elements give nullable items by the target version's rules: `Nullable<T>`, and a reference element annotated `T?` in the return type (`ActionResult<IAsyncEnumerable<Item?>>`, `Task<IAsyncEnumerable<string?>>`, …), also in the `itemSchema` of sequential media types; elements without annotations (`#nullable disable`) stay non-nullable. `IAsyncEnumerable<SseItem<T>>` from a controller is an array of `SseItem<T>` objects, as MVC writes it; server-sent events are never guessed from the type name.

- [FEATURE] An `IAsyncEnumerable<T>` response is described per declared media type. A sequential JSON media type (`application/jsonl`, `application/x-ndjson`, `application/json-seq`) gets `itemSchema: T` and no `schema` in OpenAPI 3.2; for 3.0 and 3.1 the serializer writes it as `x-oai-itemSchema`, with one warning per media type (code `media-type.item-schema-moved-to-extension`). `application/json` in the same response keeps the array. `text/event-stream` gets no schema and a warning in every version (code `response.event-stream-without-formatter`): standard MVC has no server-sent events formatter, so a custom one or `ServerSentEventsResult<T>` is needed. Global `[Produces]` filters get the same per-media-type form. `[Produces("text/event-stream")]` without a body type is unchanged.
- [BEHAVIOR] The warning unit is the topmost lost or moved node: a version warning located inside another one (for example the item schema of a QUERY operation that 3.0 moves into `x-oai-additionalOperations`) is not reported separately. Warnings about the input itself and component warnings (a component is a subtree of its own, also when reached only from a moved operation) are always reported.

- [BUGFIX] `ServerSentEventsResult<T>` responses are described as `text/event-stream` with the event schema of OpenAPI 3.2 as `itemSchema`: an object with a required string `data` (`contentMediaType: application/json`, `contentSchema: T`; a plain string for `string` and `byte[]`, which the result writes as is), string `event` and `id`, and an integer `retry` ≥ 0. For 3.0 and 3.1 the serializer writes `x-oai-itemSchema`, with one warning per media type. Previously such responses produced `application/json` with a fake component such as `StreamItemServerSentEventsResult`.
- [FEATURE] Server-sent events data is described by the HTTP JSON options (`ConfigureHttpJsonOptions`), as ASP.NET Core writes it. When those differ from the MVC options in naming policy, ignore condition, number handling or converters, a type used both by a controller body and by events data gets a second component for the HTTP context: `{Id}Http` (variants `{Derived}As{Id}Http` and the base branch `{Id}HttpDefault` of a polymorphic base follow, and the HTTP union refers only to HTTP components); a type used only by the HTTP context keeps its usual id. One warning (code `serialization-contexts.shared-types`) lists those types. The dictionary key policy does not split the contexts.

- [BUGFIX] Actions returning typed results are described by what the results write. `Results<…>` gives one response per variant; a framework result with a fixed status (`Ok<T>` 200, `Created<T>` 201, `Accepted<T>` 202, `NoContent` 204, `BadRequest<T>` 400, `ValidationProblem` 400 with `application/problem+json`, `UnauthorizedHttpResult` 401, `NotFound` 404, `Conflict` 409, `UnprocessableEntity` 422, `InternalServerError` 500, with or without a body) gives that status and its body, serialized with the HTTP JSON options; status-only results get no schema and no warning; explicit `[ProducesResponseType]` wins per status code, and `[Produces(typeof(T))]` / `[Produces<T>]` gives the 200 body ahead of the result's own value type. A result whose status is not statically known (untyped `IResult`, a user-defined result, `JsonHttpResult<T>`, `ProblemHttpResult`, …) gets a warning (code `response.result-status-unknown`) when the action declares no response; the known variants of a `Results<…>` that also contains such a result are still described, and only when no response is known at all a 200 response without a schema stands in. Previously these actions produced fake components such as `ResultItemOk`, `IResult` or `ResultItemOkAndNotFoundResults`. The requirements were correct in memory (and visible to `--validate`), but `OpenApiDocumentBuilder` created each `OpenApiSecuritySchemeReference` without a host document, and Microsoft.OpenApi writes a requirement key only if the reference resolves against its host document's `components/securitySchemes`.
